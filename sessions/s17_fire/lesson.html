Press To Fire

Everything on screen so far has existed since the moment the program started. Today you make something out of nothing, while the game is running.

What you're making

A space bar that fires. One press, one shot, straight up from the middle of the ship.

The shots never stop existing — they fly off the top of the screen and keep going forever. That gets sorted out next session.

New this session

A list can grow while the game is running. You already know append from the stars. The difference is that the stars were all made before the window opened, and these get made in the middle of a frame, because somebody pressed something.

A shot is just a dict, like everything else. An x, a y, and that is all it needs — it only ever goes one direction.

And firing needs a different question from steering. Holding an arrow key should keep moving you. Holding the space bar should not keep firing — that is sixty shots a second. The picture below is the difference.

Stuck?

Hint 1 — what is an "event"?

Something that happened, rather than something that is.

Between one frame and the next, pygame keeps a little list of everything that went on — keys going down, keys coming up, the mouse moving, the window being closed. pygame.event.get() hands you that list, and the loop you have had since Session 6 goes through it.

You have been reading one kind of event all along: event.type == pygame.QUIT is how the X button gets noticed. pygame.KEYDOWN is another, and event.key says which key it was.

Hint 2 — how do I centre the shot on the ship?

The ship's left edge is ship["x"], so the middle of it is ship["x"] + SHIP_W / 2.

But x on the shot is its left edge too, so putting it exactly at the ship's middle leaves it half a shot too far right. Take off half the shot's width:

shot = {
    "x": ship["x"] + SHIP_W / 2 - SHOT_W / 2,
    "y": ship["y"],
}

Same trick as putting a rectangle in the middle of the screen back in Session 7.

Hint 3 — why does the shot go up when I take away?
Because y counts downwards, which has been true since Session 7 and will never stop being surprising. The top of the screen is y = 0, so heading up means getting smaller.

# state.py

def make_shot(ship):
    shot = {
        "x": ship["x"] + SHIP_W / 2 - SHOT_W / 2,
        "y": ship["y"],
    }
    return shot


def update_shots(shots, dt):
    for shot in shots:
        shot["y"] = shot["y"] - SHOT_SPEED * dt


# main.py, in the event loop

def draw(screen, stars, ship, shots):
    screen.fill(BG)

    for star in stars:
        pygame.draw.rect(screen, STAR_COLOUR, (star[0], star[1], STAR_SIZE, STAR_SIZE))

    for shot in shots:
        pygame.draw.rect(screen, SHOT_COLOUR, (shot["x"], shot["y"], SHOT_W, SHOT_H))

    pygame.draw.rect(screen, SHIP_COLOUR, (ship["x"], ship["y"], SHIP_W, SHIP_H))

How it could break

Holding space fires a stream of shots The check ended up with the steering keys instead of in the event loop. get_pressed is true on every frame; KEYDOWN happens once.
AttributeError: 'Event' object has no attribute 'key' Only keyboard events carry a key. Check event.type == pygame.KEYDOWN first, and put the event.key test inside it.
TypeError: draw() takes 3 positional arguments but 4 were given draw in render.py needs a fourth slot for the shots. Both ends have to change together, as always.
ImportError: cannot import name 'make_shot' from 'state' It is not in state.py yet, or the name is spelled differently there.
The shots come out sideways from the ship The x is using the ship's left edge without adding half its width. See Hint 2.
The shots fall downwards You added SHOT_SPEED * dt instead of taking it away. Up is a smaller y.
It gets slower and slower the longer you play Not a mistake — that is the whole point of next session. Every shot you have ever fired is still up there, being moved and drawn, forever.
