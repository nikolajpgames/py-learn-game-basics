Three Lives

The ball falls past the bat, off the bottom, and keeps going forever. Nothing notices, and nothing ever ends.

What you're making

Three lives, a ball that comes back when you lose one, and a game that finishes when you run out.

All of it is Session 20's state machine, applied to a different game.

New this session

Nothing new. A counter, a check, and the mode variable from Session 20 — the same three things, wearing different clothes.

Losing the ball is one if. When the ball's y is past the bottom of the screen it has gone: take a life, and make a new ball.

And when the lives run out, the mode changes. Everything stops moving, a message appears, and a key starts it over. Exactly the shape you built for the shooter.

modeAdd a "paused" mode and a key to toggle it. Nothing moves, nothing resets, and it is about four lines.

Stuck?

Hint 1 — why make a new ball instead of moving the old one?

Because make_ball() already knows everything about where a ball starts — position, size, speed, direction. Moving the old one means setting all six of those by hand and remembering to reset the speeds as well.

Throwing the old one away and asking for a fresh one is less code and cannot get half-done.

Hint 2 — what exactly should stop when the game is over?

The moving and the hitting. Not the drawing, and not the event loop.

Drawing has to keep going or the window goes blank. The event loop has to keep going or you cannot press R, or close the window.

So if mode == "playing": wraps the updates and the collisions, and nothing else.

Hint 3 — the restart only half works

Count what a new game needs: fresh bricks, a fresh ball, the lives back to full, and the mode back to "playing". Miss any one and it goes wrong in its own way — no bricks, or instantly over again.

Four lines together in one place. If that feels repetitive, that is a fair instinct: it is the sort of thing that eventually becomes a start_game() function.

        update_ball(ball, dt)
        bounce_off_bat(ball, bat)

        ...                       # the brick code

        if ball["y"] > HEIGHT:
            lives = lives - 1
            ball = make_ball()
            if lives == 0:
                mode = "over"

    draw(screen, bat, ball, bricks, lives, mode)

Challenge

Give them a moment to get ready. After losing a life, hold the ball still on top of the bat until they press space. Losing a life and instantly having a ball flying at you is a mean way to be treated.

That needs a third mode — "waiting" — where the bat moves and the ball sits glued to it. Three modes, and the game already feels finished.

Then a score. A brick is worth more the higher up the wall it was, which is how the arcade one did it: the top row is hardest to reach.

How it could break

Lives go straight from 3 to 0 The check is running every frame while the ball is below the screen, because the new ball is not being made — or is being made below the bottom edge.
The game ends but you cannot restart The R check is inside if mode == "playing":, so it can never run. It belongs in the event loop.
Everything freezes including the window The draw call has ended up inside if mode == "playing":. Drawing has to happen whatever the mode.
pygame.error: font not initialized render.py needs pygame.font.init() before it builds its font, because it gets imported before main.py runs pygame.init(). Same as Session 20.
Lives go negative The check is if lives == 0 but something is taking one off after that. Test with <= 0 if you would rather be safe.
The restart gives you no bricks make_bricks() is missing from the reset. A fresh game needs all four things put back.

Stop while it still runs.
