Three Files

The screen looks exactly the same at the end of this one as it did at the start. What changes is the shape of the code behind it.

What you're making

Exactly what you already have — twenty boxes bouncing and flashing — but living in four small files instead of one long one.

Nothing on screen changes. What changes is that you can find things again.

New this session

A file can borrow things from another file. from config import * at the top of a file means "go and fetch everything that file made, and let me use it here as though I had written it myself".

So a program can be split up by job. One file for the numbers you fiddle with, one for the rules of the world, one for the drawing, and one to run the loop.

Every file needs its own imports. This is the bit that trips people up. Files do not share what they have borrowed — if state.py uses WIDTH, then state.py needs its own from config import *, no matter what main.py already did.

Look at where pygame ends up in the picture. state.py does not import it at all — the part that knows the rules of the world knows nothing about pixels. That is what lets you check your bouncing and your collisions are right without ever opening a window.

Stuck?

Hint 1 — what does the star in "import *" mean?

"Everything". from config import * brings in every name that file made — WIDTH, BG, all of them — and you use them exactly as before.

The other way is to name them one by one, like from state import overlaps, update, make_boxes. That is more typing but easier to read later, because you can see at a glance what came from where.

The star is fine for a settings file, where you genuinely do want all of it. It is a bit lazy for anything else.

Hint 2 — which things go in which file?

Ask what each one is for.

A number you might fiddle with — config.py.

Works out what happens, and would still make sense if the game were played over the telephone — state.py. Moving, bouncing, deciding what is touching what.

Puts something on the screen — render.py. If the line mentions screen or pygame.draw, it lives here.

Runs the loop — main.py. Ideally nothing else at all.

Hint 3 — why keep pygame out of state.py?

Because then you can run it on its own, with no window, and check that the rules work.

Later on, when a box goes through a wall and you cannot see why, being able to test the moving and the touching without anything being drawn is the difference between finding it in a minute and losing an evening.

It is also a good way to think. The rules of a game and the way it is painted are genuinely two different things, and keeping them in two different files stops them getting tangled.

# ---------- render.py ----------
import pygame
from config import *


def draw(screen, boxes):
    screen.fill(BG)
    for box in boxes:
        pygame.draw.rect(screen, box["colour"],
                         (box["x"], box["y"], BOX_SIZE, BOX_SIZE))


# ---------- main.py ----------
import pygame
from config import *
from state import overlaps, update, make_boxes
from render import draw

pygame.init()
screen = pygame.display.set_mode((WIDTH, HEIGHT))
clock = pygame.time.Clock()

boxes = make_boxes()

running = True
while running:
    dt = clock.tick(FPS) / 1000.0

    for event in pygame.event.get():
        if event.type == pygame.QUIT:
            running = False

    for box in boxes:
        update(box, dt)
        box["colour"] = BOX_COLOUR

    for a in boxes:
        for b in boxes:
            if a is not b and overlaps(a, b):
                a["colour"] = HIT_COLOUR

    draw(screen, boxes)
    pygame.display.flip()

pygame.quit()

Challenge

Give every box its own colour. In state.py, write a small function that invents one:

def random_colour():
    r = random.randint(100, 255)
    g = random.randint(100, 255)
    b = random.randint(100, 255)
    return (r, g, b)

Then use it in make_boxes so each box is built with a colour of its own instead of BOX_COLOUR.

You will hit a snag straight away: they all turn cyan again after a single frame. Something in the game loop is setting every box's colour, sixty times a second. Find it, and work out what each box needs to remember so it can go back to its own colour instead of everyone's.

Two more, if that one lands easily. The interesting part is where each of them goes.

Outlines instead of solid blocks — pygame.draw.rect takes one more number after the position, and it is the thickness of the border. Give it 3 and the box comes out hollow. Draw a box hollow when it is not touching anything, and solid when it is.

Wrap around instead of bouncing — a box that goes off the right edge comes back on the left, like Asteroids. Replace the four wall checks with something more like if box["x"] > WIDTH: box["x"] = -BOX_SIZE and work out the other three yourself.

Before you start either one, guess which file you will be opening. Then check whether you were right — you should be, every time, and that is the whole reason for having split them up.

How it could break

ModuleNotFoundError: No module named 'config' config.py is not in the same folder as main.py, or its name has a typo. They all have to sit side by side.
NameError: name 'WIDTH' is not defined — in state.py The one everybody hits. Every file needs its own imports; state.py cannot see what main.py borrowed. Put from config import * at the top of it too.
ImportError: cannot import name 'update' from 'state' That function is not actually in state.py — probably still sitting in main.py, or the cut only half-worked. Open the file and look.
NameError: name 'random' is not defined — in state.py Same rule again. make_boxes uses random, so state.py needs its own import random.
NameError: name 'pygame' is not defined — in render.py And again. render.py is the file that draws, so it is the file that needs import pygame.
Everything imports fine but the window is black draw moved out but is never called, or pygame.display.flip() got left behind in the cut. Check the bottom of the loop in main.py.

Stop while it still runs. Next arc, it becomes a game you can lose.
