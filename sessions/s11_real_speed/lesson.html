Session 11 Arc 2 · Motion & Time

Real Speed

Your box has a bug you haven't noticed yet. Change one number and it'll be obvious.

What you're making

The same sliding box — but moving at a speed you can state in actual words. "240 pixels every second", not "4 pixels every frame, and a frame is however long a frame happens to be."

Once that is sorted, the box moves at the same speed on any computer, including ones faster than yours.

New this session

Frames are not all the same length, and you can't control how long they are. A slow computer, a busy computer, a 144 Hz monitor — all different.

So clock.tick(FPS) hands you a number: how many milliseconds the last frame took. A millisecond is a thousandth of a second — there are 1000 in one second — so dividing by 1000 turns that number into seconds. That number is called dt, short for delta time, which just means "the change in time".

Then instead of "move 4 pixels", you say "move 240 pixels-per-second, times however much of a second just went by". Long frame, big move. Short frame, small move. Same real speed either way.

This is how every real game works. A game never asks "which frame is this?" — it asks "how much time has gone by?" and moves the whole world along by that much. Someone on a 144 Hz gaming monitor and someone on a laptop struggling at 30 gets the same game at the same speed. The fast machine just draws more, smaller steps in between, so it looks smoother.

And frames are never evenly spaced anyway. A frame with a hundred things on screen takes longer than an empty one, and your computer has other jobs to do. dt is measured fresh every single frame for exactly that reason.

Stuck?

Hint 1 — what does clock.tick actually do?

Two jobs at once, which is why one short line does so much.

It waits. If the frame finished early it pauses just long enough to hold you near the frames-per-second you asked for. That is the speed limiter you have had since Session 6.

And it reports. It hands back how many milliseconds have gone by since the last time you called it — a millisecond being a thousandth of a second. 1000 of them make one second, which is why / 1000 turns it into seconds.

At 60 FPS a frame takes about 16 milliseconds, so dt lands around 0.016. Put print(dt) inside the loop and watch the numbers go by.

One detail if you do: it only ever gives whole milliseconds, so at 60 FPS you will see 16 and 17 rather than a tidy 16.67. Across a whole second they even out.

Hint 2 — tick() or get_time()?

Think of a stopwatch with a lap button.

clock.tick() is pressing the lap button. It records how long that lap took, hands you the number, and immediately starts timing the next one. Pressing it changes something.

clock.get_time() is reading the last lap time off the display. It gives you the same number tick() already returned, and pressing nothing. You can read it as often as you like and it never changes.

That is why tick() belongs exactly once per frame. Every call waits for a full frame's worth of time and then measures from the call before it — so calling it twice in one frame makes your game run at half speed. It is a horrible bug to find, because nothing looks wrong.

Use the number tick() hands back. get_time() is only for when some other part of the program wants that same number and you would rather not pass it around.

Hint 3 — check the maths on 240 × 0.016
That's about 3.9 pixels — near enough the 4 you had before. So at 60 FPS nothing visibly changes. The difference only shows up when the frame rate does something you weren't expecting, which on someone else's computer it always will.
Hint 4 — why does the box only move sometimes?

If box_x starts as a whole number like 100, Python may keep chopping the fraction off every frame. At a slow speed each frame only adds a fraction of a pixel, that fraction gets thrown away, and the box never moves at all.

Writing 100.0 tells Python this number is allowed to have a decimal point. Then the fractions add up properly.

Show me a finished version 
SPEED = 240       # pixels per SECOND


def update(x, y, dt):
    x = x + SPEED * dt
    return x, y


# ... and in the game loop:

while running:
    dt = clock.tick(FPS) / 1000.0

    for event in pygame.event.get():
        if event.type == pygame.QUIT:
            running = False

    box_x, box_y = update(box_x, box_y, dt)
    draw(screen, box_x, box_y)

    pygame.display.flip()

How it could break

TypeError: update() missing 1 required positional argument: 'dt' You added dt to the def line but not to the line that calls it. Both have to change together, every time.
NameError: name 'dt' is not defined The opposite problem — you're using dt inside update but never gave it a slot on the def line.
NameError: name 'STEP' is not defined Renaming STEP to SPEED means renaming it everywhere. There's one left behind inside update.
Everything runs at half speed and nothing looks broken You have clock.tick() in the loop more than once. Each call waits for its own full frame, so two calls means two waits. There should be exactly one, at the top of the loop.
The box moves ludicrously fast You've got SPEED = 240 but forgot the * dt, so it's moving 240 pixels every single frame instead of every second. Sixty times too fast.
The box doesn't move at all, at slow speeds Whole-number problem — see Hint 3. Make the starting position 100.0.
