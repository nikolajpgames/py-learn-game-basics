Your Ship

Fifteen sessions in, and nothing you have made has ever done what you told it to. That changes now.

What you're making

A ship at the bottom of a starfield that you steer left and right with the arrow keys, and that cannot be driven off the edge of the screen.

The stars are the ones from Session 9. They have been sitting in a folder waiting for a use.

New this session

pygame.key.get_pressed() tells you which keys are held down right now. It hands back something you can ask about any key: keys[pygame.K_LEFT] is True while the left arrow is down and False the moment it comes up.

You check it every frame, in the game loop, sixty times a second. So holding a key means moving a little bit, sixty times a second, which adds up to smooth movement.

But the keyboard is a pygame thing, and state.py does not do pygame. So main.py reads the keys and works out one number — −1 for left, 1 for right, 0 for neither — and hands that to update_ship. The rules of the world get told which way, never which key.

That is worth more than it looks. Swap the arrows for A and D, or a gamepad, or make the ship follow the mouse, and only one line in one file changes.

Stuck?

Hint 1 — what does get_pressed() actually give me?

A long row of True and False values, one for every key on the keyboard, describing this exact moment.

You look a key up by name: keys[pygame.K_LEFT], keys[pygame.K_SPACE], keys[pygame.K_a]. Those K_ names are pygame's numbers for the keys, and there is one for everything.

It has to be called fresh every frame. Call it once before the loop and you get a snapshot of one instant, frozen forever.

Hint 2 — why not just move the ship in main.py?

You could. It would work today.

But update_ship is where the rules live, and rules are worth keeping in one place. Right now it is one line; by the end of the arc it will also stop the ship at the walls and remember whether it is alive.

Handing it a plain number rather than the keyboard is what keeps it that way. The function does not care whether the player pressed an arrow, leaned a joystick, or whether you are testing it with update_ship(ship, -1, 0.016) and no keyboard at all.

Hint 3 — holding both arrows does something odd

It goes right. Look at the order the two ifs run in: left sets direction to −1, and then right overwrites it with 1.

That is not a bug so much as a decision you have accidentally made. If you would rather both-at-once meant "don't move", change the second one to elif — or work out a way to add them together instead.

# main.py, inside the game loop

    keys = pygame.key.get_pressed()

    direction = 0
    if keys[pygame.K_LEFT] or keys[pygame.K_a]:
        direction = -1
    if keys[pygame.K_RIGHT] or keys[pygame.K_d]:
        direction = 1

    update_ship(ship, direction, dt)


# state.py

def update_ship(ship, direction, dt):
    ship["x"] = ship["x"] + direction * SHIP_SPEED * dt

    if ship["x"] < 0:
        ship["x"] = 0
    if ship["x"] + SHIP_W > WIDTH:
        ship["x"] = WIDTH - SHIP_W

Challenge

Make the stars drift downwards, so it looks like the ship is flying forwards. A star that falls off the bottom comes back on at the top, at a new random x.

The stars are tuples, and tuples cannot be changed — so this is the moment they need to become something else. Dicts, most likely.

If you want it to look properly good: give each star its own speed as well, slow ones and fast ones mixed together. Distant things move slowly and near things move quickly, and your eye reads that as depth without being told.

How it could break

The ship does not move at all keys = pygame.key.get_pressed() is outside the loop, so it was read once at the start and never again. It has to be inside, running every frame.
NameError: name 'keys' is not defined The get_pressed line is missing, or sits below the lines that use it. Python reads top to bottom.
AttributeError: module 'pygame' has no attribute 'K_Left' Capitals matter: it is K_LEFT, shouting. Same for K_RIGHT, K_SPACE.
The ship jumps across the screen instead of gliding The * dt has gone missing, so it is moving 420 pixels every frame rather than every second.
NameError: name 'SHIP_W' is not defined — in state.py That file needs its own from config import *. Files do not share what they have borrowed.
The ship stops before the edge, or hangs over it ship["x"] is the ship's left side. To keep its right side on screen you have to compare ship["x"] + SHIP_W against WIDTH, the same as the boxes bouncing off walls.
